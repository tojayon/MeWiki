# MeWiki 社区插件生态设计提案

状态：长期生态设计，P0 统一契约、P1 声明式本地安装及 API v2 图文模板导出已落地。最近更新：2026-11-11。外部内容使用[声明式 API v1](API_V1.md)，数据导出使用 [API v2](API_V2.md)；可执行隔离环境、通用编辑器贡献点与社区目录仍是后续设计。

当前安装流程、作者工具及实现导航见[插件开发入口](README.md)，执行顺序见[阶段路线](../plans/2026-11-10-plugin-ecosystem.md)。本文描述目标架构；未在正式 API 参考中发布的字段和函数不能视为现有能力。

## 社区生态通常如何运转

一个完整生态包含开发、分发、安装、运行和维护：

1. 项目提供有版本的插件 API、类型、示例、开发调试工具和兼容策略。
2. 作者用独立仓库开发插件，构建包含清单、资源和必要代码的发行包。
3. 作者发布包和版本记录，向社区目录提交元信息；目录帮助用户发现插件，也提供维护者、兼容范围和审核信息。
4. 用户下载包本地安装，或从目录选择安装；MeWiki 检查包、版本和能力请求，经用户操作启用。
5. 插件通过受限接口贡献功能，应用统一管理资料写入、界面入口、异常和停用。
6. 作者维护更新，项目管理废弃 API、失效来源、撤回版本和兼容测试；用户可以拒绝升级、停用和卸载。

早期无需自建账户、上传后台和支付系统。使用 GitHub 仓库、Release 文件与经审查的静态目录，就能建立开源社区的第一版分发流程。本地安装应独立可用，网络目录不可用时已有插件和资料仍能工作。

## 路径选择

| 方式 | 成本与边界 | MeWiki 的安排 |
| --- | --- | --- |
| 插件提交到主仓库，随应用构建 | 经源码审查、随应用升级 | 随附清单与独立包使用同一契约与执行器 |
| 下载 JS 后直接在主页面加载 | 开发容易，代码同时获得主页面资料、存储与请求能力；清单里的权限无法限制它 | 不作为社区代码加载方式 |
| 声明式扩展，加隔离执行与能力代理 | 先提供受限数据贡献，再提供独立代码执行边界 | 声明式内容与本地安装已提供，隔离执行待实现 |

独立进程扩展宿主适合未来桌面版或确需本地计算的扩展。当前应用为浏览器加 Node 本地服务，先做进程宿主会增加跨平台安装与权限成本，留待明确场景出现。

## 六个组成部分

- **插件 API 与开发工具**：独立公开类型和运行契约；作者不导入 MeWiki 内部组件、store 或 `src/` 路径。
- **清单与贡献点**：声明身份、版本、内容类型、导出模板及能力请求。通用命令、面板、导入器和可执行导出器后续按同一机制扩展。
- **运行宿主与能力代理**：管理加载、取消、异常、消息与授权；统一登记界面入口，统一执行资料操作。
- **安装器与包仓库**：验证、暂存、原子安装、版本切换、回滚和卸载；下载包不立即执行代码。
- **插件设置与数据**：记录安装来源、启停、授权和按库隔离的数据；保留当前应用级启停语义。
- **社区目录与治理**：负责发现、版本元信息、来源验证、审核与撤回，不承载用户笔记。

```mermaid
flowchart LR
  A[作者独立仓库] --> B[构建发行包]
  B --> C[本地安装器]
  B --> D[经审查的社区目录]
  D --> C
  C --> E[清单校验与版本仓库]
  E --> F[声明式贡献或隔离运行环境]
  F --> G[插件宿主与能力代理]
  G --> H[MeWiki 界面和现有保存流程]
  H --> I[当前资料库]
```

目录、包和插件运行环境都不能直接获得资料库路径或绕过既有保存链路。

## 先保持三条协议边界

1. **外部宿主协议**继续使用 `mewiki.integration` v1，负责外部程序临时上下文和来源定位。其 `context.read` 表示 MeWiki 接收外部上下文，不表示外部程序读笔记。
2. **插件 API**使用独立版本；已提供声明式内容 API v1 与数据导出 API v2，代码生命周期、可执行贡献点和能力代理尚未开放。API v2 的数字不代表宿主通信或笔记内容格式升级，不能将现有宿主 SDK 宣传为可执行插件 SDK。
3. **笔记内容协议**继续使用 `external` 块及 provider、内容类型、`schemaVersion`、通用可读字段和 `data`。插件包升级和插件 API 升级不自动提高内容版本。

应用版本、包版本、清单版本、插件 API 版本、宿主协议版本和内容版本分别校验。比如“插件 2.0.0 支持内容版本 1”是正常情况。旧 `evidence` 和 `webbench-research-library` 交换格式继续兼容。

## 已实现的发行包与后续清单扩展

当前支持 JSON 清单及 ZIP 容器，扩展名可为 `.mewiki-plugin`。第一版 schema、视图、表单和来源规则均内联在清单中，包内只允许清单及可选说明、许可证，不支持单独资源文件或可执行入口。完整字段与大小限制见 [API v1](API_V1.md)。后续隔离代码能力验收完成，再评审 runtime、资源及权限扩展。

以下是当前可校验的最小声明式内容插件；完整表单示例见[测量记录](../../examples/plugins/measurement/manifest.json)：

```json
{
  "manifestVersion": 1,
  "apiVersion": 1,
  "id": "org.example.instrument",
  "name": "测量记录",
  "version": "0.1.0",
  "description": "把外部测量记录保存为可读卡片。",
  "capabilities": ["context.read"],
  "contentTypes": [{
    "id": "measurement",
    "schemaVersion": 1,
    "insertionLabel": "插入测量记录",
    "schema": { "type": "object" },
    "view": []
  }]
}
```

当前 API 使用精确整数版本，不接受 `engines` 范围、作者声明、权限别名或 `contributes`。包实现版本按完整三段版本身份保存，可带预发布和构建标签，不按字符串比较新旧。版本范围、发布者认证与代码权限需在对应阶段单独定义。

`id` 是稳定机器身份，显示名称可改。首期一个插件只声明自己的 provider；现有 WebBench 保持 `org.mewiki.webbench`。内容类型与命令 ID 均归属该插件命名空间，禁止覆盖其他插件或核心入口。ID 格式和包内路径分开校验，不能直接将用户提供的 ID 当作可信文件路径。

当前 schema 为内联的受限结构描述，禁止 `$ref`；限制深度、字段数和输入大小。视图由核心提供的文本与数值字段组成，来源链接只由用户点击触发，不允许原始 HTML、表达式求值或脚本。资源文件和自定义视图仍需后续设计，运行时不使用 CDN。

## 逐步开放的贡献点

**外部内容（已实现）。** 内容类型登记、结构校验、通用表单、可取消的本机目录查询、只读卡片和用户发起的来源打开均使用声明式 API v1。WebBench 的实验选择、时间范围、环路、连接和来源都已迁入清单，没有独立 React 分支。

**图文导出（已实现数据贡献）。** API v2 声明模板与画幅，核心读取用户明确选择的快照、解析本地资源、生成静态 PNG/JPEG 并下载。官方社交图文与独立发布示例使用同一契约；没有插件脚本，也不把整库或目录交给模板。此分支可在 P2 之前独立实现和验收，不代表通用命令、面板、导入器或可执行导出器已经开放。

**命令。** 后续提供命令登记与执行，宿主统一安排菜单、快捷键、可用条件和忙碌状态；登记返回可释放的资源。插件只处理被授予的当前上下文，不持有整个应用状态。

**面板。** 后续允许在宿主指定区域显示受限视图或隔离界面，核心控制尺寸、焦点、关闭、主题和错误占位。插件 CSS 与 DOM 不进入主编辑器，也不能改变左右侧栏开关和 44px 顶栏规则。

**通用导入导出（后续）。** 除已实现的图文数据贡献外，后续核心向可执行插件提供用户选中的输入和获准资料快照。插件返回候选结果，核心验证并展示导入预览，用户确认后通过既有 controller 保存；导出由核心提供下载。不开放任意磁盘路径、批量库扫描和后台覆盖。

通用命令、面板和可执行导入导出仍是后续能力说明，尚无可调用的 `registerCommand()` 等公开函数；实现时再发布对应类型、示例与参考文档。已实现的图文数据贡献以 [API v2](API_V2.md) 为准。

## 运行隔离与能力代理

当前随附插件和独立包均为声明式数据，由统一核心执行器渲染；没有第三方代码加载能力。后续可执行插件不得由主页面 `import()`，也不通过 `eval`、`new Function`、Node `vm` 或 npm 安装脚本执行。

后续界面插件可采用不含 `allow-same-origin` 的 sandbox iframe，纯计算扩展可由受控隔离页面创建 Worker。单独使用 Worker 不会隔离网络或同源存储，不能视为权限边界。实施前必须证明以下限制成立：

- 插件无法读主页面 DOM、应用 localStorage、IndexedDB、cookie 或主应用保存令牌；无法直接请求资料库、附件及安装管理接口。
- CSP 限制脚本来源、动态代码、连接、图片、字体、子框架和表单；只从校验后的本地包加载资源，不启用运行时 CDN。外网请求经能力代理进行，重定向后重新核对目标地址。
- 本地 API 继续校验 loopback、Host、Origin 与写入请求标记，并补齐隔离环境的对抗检查；不得向插件 iframe 增加读取资料库的 CORS 放行。现有本机检查不能替代这些验证。
- 消息先由父页面核对准确的发送窗口和随机会话，再建立专用 MessageChannel。opaque origin 的 `null` 不能作为身份凭据；严查操作、参数结构、长度、深度、请求数、超时与重复请求。
- 宿主授予的每项能力绑定插件 ID、具体安装版本和会话。涉及资料的能力还绑定当前库 ID、笔记/选择和用户操作；插件传来的身份或库 ID 不作为授权依据。

manifest 中的能力请求只有经宿主校验才生效。建议分开设计外部上下文、打开来源、读取用户选择、提出内容插入、网络请求与插件私有存储；网络授权细化到目标 origin，读取资料的授权限定资料库和范围。权限增量在升级启用前重新确认，不能把旧 `enabled` 状态当作对新增资料读取的同意。

外部内容插入、来源打开、导入与覆盖仍需用户明确触发。只读转换或分析可以在用户启动的任务内执行，结果写入由核心确认；不默认开放后台写入、任意文件系统、进程执行和系统命令。声明式包没有可执行入口，也要验证 URL、资源和字段渲染，不能仅凭“没有 JS”认定所有输入可信。

## 生命周期与异常

安装只落盘，启用才登记贡献并建立运行会话。隔离运行环境就绪后才显示可执行入口；失败显示插件级错误，笔记仍可打开。建议生命周期为启用、激活、停用、释放，具体函数签名在插件 API 阶段确定。

停用、卸载、升级、切库和窗口销毁都清理相应订阅、定时器、命令和面板，取消未完成请求。切库不必卸载应用级插件，但必须销毁旧库能力并丢弃迟到结果。跨窗口变更需要明确版本与状态通知，不能让旧窗口继续保存已撤销授权的结果。

运行崩溃或超时只影响该插件；允许在不启动第三方插件的恢复模式下进入设置。日志按插件与版本区分，默认不记录正文、附件内容、访问令牌或真实目录。资源配额和重复崩溃停用策略应有可复现的测试。

## 安装、升级、回滚与卸载

当前包保存在应用管理的 `.mewiki/plugins/`，隔离设置默认使用 `<设置文件>.plugins`，不放进用户资料库。原包使用摘要定位，登记保存插件 ID、版本和当前选择；安装预览及列表显示来源为本地文件。各次锁申请使用带 PID 和随机身份的独立文件，避免多个恢复者删除新持有者的锁。具体布局和兼容行为见[开发入口](README.md)。

以下为当前安装流程与后续联网分发要求；目录来源认证、代码会话和权限增量属于后续阶段：

1. 用户选择包或目录中的具体版本，先读取清单和来源，显示兼容范围、请求能力与变更。
2. 在独立临时目录检查文件数量、压缩与解压大小、压缩比、重复/大小写冲突路径、绝对路径、盘符、`..`、符号链接、入口与资源边界。限制常量需在实现时明确并覆盖测试。
3. 校验整个包的 SHA-256；目录安装时还核对可信版本元信息。摘要只证明字节一致，包自己携带的摘要或签名不能证明作者身份。本地包显示其实际来源，不能自称官方。
4. 校验成功才原子登记新版本；失败清理本次暂存，旧版本和状态保持可用。并发安装、更新和卸载通过应用级锁串行化，拒绝覆盖不同来源占用的同一 ID。
5. 升级先准备新版本，再撤销旧会话、切换和激活；新增能力待用户决定。首期只提供检查和手动更新，避免无提示更新代码或权限。
6. 回滚只切回仍可用的旧代码和设置快照，不恢复整库旧备份，也不撤销用户后来写的笔记。新版内容不被旧代码理解时使用通用卡片显示。
7. 卸载移除执行代码和登记，保留笔记、附件、未知内容 JSON 及插件资料。需要清理插件私有数据时提供独立、明确的用户操作。

插件包下载不执行 `npm install`、`postinstall` 或其他生命周期脚本；依赖应由作者构建到发行包。禁用运行时远程脚本和隐式依赖下载。

## 配置、资料与兼容迁移

保持现有同一来源浏览器配置中的应用级启停语义。包安装状态由本地服务管理，启停偏好与授权另存；不能把本机装了包等同于所有浏览器、窗口和库都授权启用。旧 `mewiki:plugins:v1` 的读取与兼容路径保留，迁移不得删除未知状态或自动添加新授权。

可读设置分为应用偏好、按资料库的插件设置，以及 `(libraryId, pluginId)` 隔离的私有数据；全部使用 MeWiki 命名空间。当前个人导出模板由本地服务保存，提供含内联图片的独立 JSON 导入导出，卸载保留且不自动混入资料库备份；通用插件私有存储仍未开放。令牌不写入笔记、manifest、公共目录或普通资料备份，凭据存储能力未提供时不承诺支持它。

安装包、可执行代码和机器授权不随资料备份自动恢复。用户内容及插件生成的持久资料必须能完整导出恢复；新增私有存储前先定义其便携数据格式、附件引用和按库备份规则，不能留下只存本机缓存的唯一副本。

内容迁移先读取、预览，再由核心备份并按正常保存流程提交；失败保留原 JSON。插件升级不扫描并改写所有库，不删除用户备注或未知字段。卸载后无需运行插件仍可读取通用内容。

## 社区目录与维护

首版目录可以是独立 Git 仓库中的 JSON，由 PR 审查维护，记录插件 ID、作者仓库、许可证、说明、版本、兼容范围、下载地址和包摘要。发行文件可托管在作者 GitHub Releases；目录控制方和信任根由 MeWiki 明确配置，不能接受下载包自带的“可信作者”声明。

官方与社区使用同一清单、兼容校验和能力模型，未来发布者标识来自目录验证。现有随附插件已经使用同一声明式执行器；后续官方独立包也走同一安装链路，不能通过名字或 `org.mewiki` 前缀自动获得特权。

目录审查先检查来源、许可证、构建说明、请求能力、兼容测试和维护渠道。文件摘要不代表代码无风险；官方标识与审核状态也要说明验证范围。撤回版本停止新安装并给已有用户显示原因，不能远程删除用户资料；断网时使用缓存状态，恢复网络后才能获知新的撤回信息。

作者工具逐步补齐模板、开发模式、清单校验、打包、内容往返和权限检查。开发模式需要用户主动开启且有明确标识；生产安装不加载任意本地工作目录。提供迁移指南、废弃周期与兼容测试，比先做评分、搜索排序和账户体系更有价值。

## 设计参考与后续决定

可参考 [VS Code Extension API](https://code.visualstudio.com/api) 的贡献点与版本契约、[扩展宿主](https://code.visualstudio.com/api/advanced-topics/extension-host)的生命周期，以及 [Obsidian 社区插件](https://help.obsidian.md/community-plugins)的发现与安装体验。它们的执行权限和平台条件不同，MeWiki 需要单独实现自己的边界。

后续阶段还需确定：可执行消息契约、资源配额、隔离启动方案、目录信任根、发布者和签名策略。当前声明式内容与图文数据导出契约分别写入 [API v1](API_V1.md) 和 [API v2](API_V2.md)；其余能力先完成[阶段路线](../plans/2026-11-10-plugin-ecosystem.md)的验收，再发布对应参考。
